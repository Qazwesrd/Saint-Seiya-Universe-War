# 多阵营角色创建与新手进程（阶段 7）

## 目标规则

- 新角色创建时可选择阵营与该阵营可用的职业/角色模板。
- 现有 32 个战斗职业模板全部至少映射到一个阵营；同一战斗模板可在不同阵营使用阵营化显示名，直至对应专属模型、动作和技能通过验收。
- 12 个阵营入口：圣域、暗黑圣斗士、海界、冥界、神界/天界、北欧仙宫、钢铁圣斗士、蓝冰战士、堕天使、泰坦神族、巨人族、鸿蒙神域。
- 鸿钧老祖是鸿蒙神域中的可选角色预设，身份标记为本游戏至高神；当前复用阿波罗战斗职业模板，专属技能、模型和动作仍是独立美术/战斗交付项。
- 鸿钧老祖的新手任务支持圣域与鸿蒙神域两个入口，进度共用同一份本地存档。
- 新角色记录阵营出生地区标识，并启用阵营新手试炼。
- 1—9 级使用阵营新手试炼追踪；10 级前不向新角色开放动漫篇章任务入口。
- 神明/天斗士可在创建时选择；新角色启用故事平衡数值，避免初始职业选择导致等级 1 的战斗数值失衡。GM/后续专属模式可另行调整。

## 当前实现边界

本阶段建立了阵营目录、创建界面、角色档案字段、新手任务进度、导师交互入口、阵营主题化起始区域原型、训练敌人/首领自动生成和 10 级剧情门槛。起始区域目前为同一场景内的程序化主题化区块，并非12张独立完整地图；阵营导师 NPC 仍复用通用模型；鸿钧老祖角色额外生成圣域与鸿蒙两个可交互任务入口。训练敌人与训练首领拥有独立的阵营 archetype 数据，并以竞技场基础数值模板派生；不代表已制作专属怪物模型。现有战斗模板不等于每个阵营职业已经拥有最终专属模型与技能动画。

## 后续验收

1. Godot 4.4.1 headless 导入和框架冒烟测试。
2. Android 新建存档，逐阵营检查出生地区标识、职业列表和新手任务保存。
3. 验证鸿钧老祖可创建，并从圣域/鸿蒙两个任务入口共用任务进度。
4. 验证 1—9 级动漫主线锁定、达到 10 级后解锁。
5. 再制作并验收每个阵营的独立地图、导师 NPC、角色外观、专属训练敌人、专属首领和技能演出。


## 阵营新手遭遇（程序化战斗原型）

12个阵营的新手试炼现在分别解析到独立的训练敌人与训练首领战斗配置，不再直接复用银河竞技场守卫与训练 Boss 的原始配置。各阵营配置有独立名称、材质主色、基础生命/攻击数值；首领还会选择对应的特殊攻击类型。相关配置由 `EnemyDatabase.get_tutorial_archetype_id()` 和 `EnemyDatabase.get_archetype()` 提供，并由新手遭遇生成器按角色存档中的阵营 ID 调用。

这一步实现的是独立战斗数据与程序化外观配色，不等于已经完成12套独立的高精度敌人模型、骨骼动画、专属技能特效或配音。正式美术资产仍需后续制作与设备实测。


## 阵营装备外观与时装槽（数据/存档阶段）

- `CharacterVisualCatalog.FACTION_ARMOR_FAMILIES` 为12个阵营提供独立装备家族、主金属/辅色、头盔、胸甲、肩甲、腰甲和腿甲轮廓标识。
- 暗黑圣衣使用黑色/石墨灰/暗银/钢蓝色；冥衣使用黑紫色。二者拥有不同 `palette_family`、金属底色和部件轮廓，不能再共用紫色暗黑配色。
- 海界使用层叠鳞片轮廓；北欧仙宫使用符文神斗衣；钢铁阵营使用机械核心、传感头盔和伺服腿甲；其他阵营也有各自家族定义。
- `COSTUME_APPEARANCES` 将夏季、圣诞、校园、休闲、王子礼服定义为独立服装，不叠加圣衣、不自动生成披风。
- 角色存档新增独立 `appearance_state.equipped_costume` 与 `costume_visible` 字段，并提供 `RPGState.equip_costume()` / `set_costume_visible()` 操作，不覆盖五件圣衣装备槽。
- 当前交付为可验证的外观配置与时装存档槽；程序化/最终角色模型的部件网格、骨骼动画、不同角色站姿、时装实际换装渲染仍需 Godot 场景实机验收和后续美术资产制作，不能把配色数据视为最终3D建模完成。


## 玩家装备实际渲染接入（程序化网格原型）

- `player.gd` 的角色装备生成现在读取角色存档中的 `faction_id`，把阵营外观配置的金属色、饰边色和强调色应用到实际装备网格。
- 程序化网格按装备家族生成差异部件：暗黑圣衣的石墨钢蓝尖刺肩甲、冥衣的黑紫肋甲、海鳞衣的鳍状肩部、钢铁装甲的胸部反应核心与伺服腿部、北欧神斗衣符文饰片、神圣衣/天衣、冰甲、堕天装甲、刻衣、巨人重甲和鸿蒙神甲的家族化轮廓。
- 时装槽现已接入玩家渲染：装备时生成独立布料网格（躯干、袖子、裤装和领口/装饰），隐藏圣衣/冥衣网格；脱下或隐藏时装后恢复装备网格。该原型不生成披风，也不把时装作为圣衣叠加层。
- 如果存在已制作的授权角色/装备 GLB 模型，仍按原有资源路径加载；时装显示时暂不叠加授权圣衣模型，避免时装被盔甲遮挡。
- 这一步是 Godot 程序化网格实际接入，不等于最终高精度角色模型、精细拓扑、完整骨骼绑定或所有角色独特站姿已经完成。需要 Godot 4.4 headless 与 Android 实机运行确认材质、网格位置和性能。
